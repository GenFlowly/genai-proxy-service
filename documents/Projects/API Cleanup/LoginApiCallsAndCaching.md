## Cross-cutting observations (updated 2026-10-30 after the cleanup pass)

- **Only #2 (/providers) ever skips a network call.** #3/#4 use the identical `createCachedResource()` shape but deliberately never skip-on-hit (render seed only); #7–#10 are paint-then-always-refetch (`staleTime: 0` equivalent); #11 has no caching at all (by decision below).
- ~~Heaviest waste: #4 vs #6~~ **FIXED** — the agents fan-out now runs once; `AgentPickerWidget` shares `customerAgentsCache`.
- ~~Per-conversation Message-table Queries for vendors~~ **FIXED** — vendors are denormalized onto the Conversation row; old rows heal on first listing.
- **`CustomerVendorApiKeys` is still hit with different access patterns**: one Query returning all rows (#1) vs per-vendor point GetItems (#7, and #5 when Settings opens) — inherent to `/models` needing decrypted keys.
- **`CustomerProfile` is read on every single request** — still true; fewer requests per login now (#5 and #6 left the login burst), but each remaining call pays the auth GetItem.
- **Prefetch bundle fires for not-yet-onboarded customers**: still true for #2–#4 (`useDefaultsPrefetch` gates only on `customerId`); the expensive member (#5) no longer rides in the bundle. A `onboardingCompleted` gate remains an open option.
- **Backend caches invisible to the frontend**: #2's process-lifetime Kotlin `providerCatalogCache` and #5's per-(customerId, vendor) probe-cache table.
- **Login burst after this pass**: `/onboard` + `/providers` + `/request-agents` + `/agents` (once) + `/models` (once) + `/conversations` + `/conversations/pinned` + `/projects` = 8 calls, down from 11, with the Message-table read amplification gone entirely.

- [x] **Stop fetching `GET /api/v1/embedding-models` at load time — fire it only when the Settings page is opened.** *(DONE 2026-10-30: removed `embeddingModelsCache.fetch` from `prefetchDefaultsPageData`; `EmbeddingModelDefaults` self-fetches on Settings mount as before.)*
  - Why it fires at load time today: purely the `useDefaultsPrefetch` warm-up. The hook's own comment gives the rationale: "the embedding-model catalog in particular can take seconds server-side" (`useDefaultsPrefetch.ts:8`) — probing vendor APIs for available models was slow, so the bundle pre-warms the cache so Settings renders populated on first visit.
  - That rationale is mostly obsolete: the backend now keeps its own per-(customerId, vendor) probe cache with stale-while-revalidate, so a cold Settings visit is no longer a multi-second wait — only the first-ever probe for a customer is slow.
  - Its only consumer is `EmbeddingModelDefaults.tsx` (Settings → Defaults), which already does its own cached-paint-then-fetch on mount (`EmbeddingModelDefaults.tsx:57-61`) — removing the prefetch changes nothing for the page.

## Decisions

- **Conversation content (#11) stays uncached — decided 2026-10-30.** Three reasons: localStorage is ~5MB/origin with a synchronous API and full histories (message text, tool results, web sources, thinking steps) would blow the shared quota; the response carries in-flight durable-run placeholders used to reattach to live streams after reload, which must never be served stale; and it would persist full conversation content at rest on the machine. Benefit is also minimal — it only fires on deep links/refreshes.
